# 进入 AITP-agent 开发工作

这是随仓库维护的开发 Skill，服务于 `packages/`、`apps/` 中的 Harness 应用和 `docs/agent/` 科研设计。`agent/` 保留旧 Pi 实现与证据，不是新主线。
它不属于上游 `plugins/aitp` 可移植科研协议（本仓库通过 `aitp/` 子模块连接），也不要求安装到全局 Skill 目录。
下列链接均相对于本文件；使用者应在目标仓库中解析它们。

## 先恢复本次任务与已有边界

先确认用户当前要做的是设计、实现、审阅还是查询现状，保留此前仍有效的授权。
普通“继续”恢复已授权任务；设计讨论本身不启动实现阶段。

1. 读根目录 [AGENTS.md](../../../AGENTS.md)，再检查修改路径适用的局部指令。
2. 读 [current.md](../../../current.md) 的入口说明和与任务相关的问题。
   它用于找到设计缺口、争议、纠错证据和下一步验证，不是另一份进度总表。
3. 读 [14 开发规划](../../../docs/agent/14-implementation-blueprint.md) 的当前状态、
   授权范围及相关阶段；以这里维护的实际边界决定可以推进什么。
   不把旧阶段编号、历史测试通过或 reviewer 同意当作新阶段授权。
   Harness 底座、aitp-agent 命名和 GPT 适配已获授权；不得再次把宿主选择当成待批准提案，也不能将其扩大为全部科研模块或真实笔记写入授权。
4. 如将改变行为或设计，读 [10 架构](../../../docs/agent/10-project-workspace.md)
   的受影响部分和 [13 科研场景](../../../docs/agent/13-research-journeys.md) 的相关 case。
   先说明这次解决什么具体问题，再选择实现或验证方式。

复用本会话仍然有效的读取和结论。除非问题涉及整体协调，不要每次通读全部设计文件。
发现 owner、事实或引用变化时，重读相关来源；不要用旧摘要替代当前状态。

| 本次问题 | 需要定位的材料 |

| 导航、资源阅读器、来源选择、任务与界面状态 | [12 界面设计](../../../docs/agent/12-desktop-interface.md) 的相关流程，以及实际 workbench 组件 |
| 新实现/API 是否已有、修改跨哪些模块 | [Harness 架构](../../../docs/architecture.md)、[AITP 服务映射](../../../docs/agent/10-project-workspace.md#harness-service-mapping)，以及 `packages/`、`apps/` 的服务定义、provider、consumer 和局部指令 |
| 旧 Pi 缺陷或契约为什么保留 | [09 旧契约入口](../../../docs/agent/09-contracts.md)、[旧 protocol](../../../agent/packages/protocol/src/)、[core](../../../agent/packages/core/src/contracts.ts)、[runtime](../../../agent/packages/runtime/src/contracts.ts)；只作为语义/历史证据，不直接当新 API |
| 某能力是否验证过、失败发生在哪一步 | [Harness 集成证据](../../../agent/notes/harness-integration.md)或[旧 Pi 集成记录](../../../agent/notes/integration.md)中的对应记录及实际测试/源码；两种宿主证据分开，避免重跑无关检查 |
| 旧审阅结论是否仍适用 | [15 设计审阅](../../../docs/agent/15-design-review.md) 中的审阅范围、时间与限制，再核对后来变动 |

源码与契约说明当前实现，架构说明目标，验证记录说明实际检查过的范围。
底层接入优先实现重要科研记忆的选择、交付、压缩恢复和维护；用户明确反对固定科研动作约束。AI 依据上下文自主选择常规下一步，明确用户要求和既有宿主权限继续适用，缺失前提提示不等于统一动作禁令。
Harness 有工具、会话、子任务、设置和桌面，不代表 AITP 约定、必要前提、审阅、写回及选择性 UI 已经实现。新功能优先使用其服务/事件和配置组合，不运行第二套 Pi agent loop；保留普通科研文件、运行状态和可重建索引的归属区分。
stub、模拟交互、排队审阅、工具成功和研究者验收应分别表述。
缺少证据时保留不确定性；不要把计划功能写成已完成。

## 推进与选择

沿用用户确定的默认自主性：目标与边界由研究者确定，AI 自主选择常规下一步；
改变核心假设、算法或研究方向时讨论，除非本次任务已明确委托该选择。
已有授权内的普通检查、修复和相关验证继续进行，不重复请求确认。
若接口或架构必须调整，先在原有 owner 中明确变化，再推进依赖它的工作。
当前阶段和新增能力的权限始终回到 14 与真实用户指令判断。

把具体故障与未实现计划区分开：指出触发条件、影响、来源、可能取舍及可区分的验证。
优先用小任务暴露错误，不为文档维护引入新 runtime、状态数据库或评估框架。

## 同一变更中维护记录

开发、设计、架构或实现证据发生变化时，在交接或声称完成前同步更新
[current.md](../../../current.md) 和受影响的原有文档：

- current.md 更新相关问题的判断、证据、剩余风险或纠正结果，并链接具体 owner。
  新发现值得后续开发者处理的缺口时补入；解决后说明依据，不仅把条目标为“完成”。
- 10 维护组件职责、合作关系、接口和设计边界；11/12 维护各自的详细规则。
- 14 唯一维护阶段、授权范围、依赖、进度和验收证据。
- 13 维护具体科研场景的实际支持、失败例和适用性；详细检查记录留在 `agent/notes/`。

不要复制一套完整计划到 current.md，也不要增加会话日志或平行总结。
只读查询、没有持久变化的审阅以及未受影响的文档不需要仪式性改写。
发现问题但本次无权修复时，在允许的文档范围内记录明确缺口，不代替授权实施修改。

## 验证与保护现有工作

文档变动检查相关链接、表述一致性和 Skill frontmatter；应用变动运行与行为相关的检查。
报告源码观察、历史记录、实际本轮验证及尚未验证的部分，保留已知失败。
保护既有 dirty work、私人研究资料和原始输出；不擅自提交、推送、重置、恢复或迁移。
设计/文档工作不隐含真实科研笔记写入。所有 hash 相关检查继续禁用。
